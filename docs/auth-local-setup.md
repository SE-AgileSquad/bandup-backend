# Run the authentication API and Swagger locally

Run the commands below from the repository root. You need the .NET 10 SDK and Docker
Desktop with its Linux engine running. The frontend and Worker are optional for these auth
calls; the API still connects to PostgreSQL, Redis and RabbitMQ at startup.

## 1. Configure the dependency stack

Create the ignored environment file if it does not already exist:

```powershell
if (-not (Test-Path -LiteralPath infra/env/dev.env)) {
    Copy-Item -LiteralPath infra/env/dev.env.example -Destination infra/env/dev.env
}
```

Edit `infra/env/dev.env`. Use your chosen local passwords in place of `CHANGE_ME`. This
example uses alternative Redis and RabbitMQ ports:

```dotenv
POSTGRES_USER=bandup
POSTGRES_PASSWORD=CHANGE_ME
POSTGRES_DB=bandup
RABBITMQ_DEFAULT_USER=bandup
RABBITMQ_DEFAULT_PASS=CHANGE_ME
POSTGRES_PORT=5432
REDIS_PORT=16379
RABBITMQ_PORT=15673
RABBITMQ_MANAGEMENT_PORT=15672
```

Start Docker Desktop, then verify the engine and start the dependencies:

```powershell
docker info
docker compose --env-file infra/env/dev.env -f infra/docker/docker-compose.dev.yml up -d --wait
docker compose --env-file infra/env/dev.env -f infra/docker/docker-compose.dev.yml ps
```

Changing environment-file passwords does not replace credentials already initialized in
existing database or broker volumes. Keep the existing credentials or deliberately recreate
the disposable local stack. The existing README documents the data-removing `down -v` command.

## 2. Configure user secrets

The API and Worker already have `UserSecretsId` values; `dotnet user-secrets init` is not
needed. `set` overwrites individual values. If you intentionally want to reset the two
project stores, preserve any keys you still need before running:

```powershell
dotnet user-secrets clear --project src/BandUp.Api
dotnet user-secrets clear --project src/BandUp.Worker
```

Use the same usernames, database name, passwords and host ports as `dev.env`. The following
PowerShell prompts keep actual passwords out of this document:

```powershell
$bandupDbPassword = Read-Host 'PostgreSQL password from dev.env'
$bandupRabbitPassword = Read-Host 'RabbitMQ password from dev.env'
foreach ($bandupProject in @('src/BandUp.Api', 'src/BandUp.Worker')) {
    dotnet user-secrets set 'ConnectionStrings:Default' "Host=localhost;Port=5432;Database=bandup;Username=bandup;Password=$bandupDbPassword" --project $bandupProject
    dotnet user-secrets set 'Redis:ConnectionString' 'localhost:16379' --project $bandupProject
    dotnet user-secrets set 'RabbitMq:Host' 'localhost' --project $bandupProject
    dotnet user-secrets set 'RabbitMq:Port' '15673' --project $bandupProject
    dotnet user-secrets set 'RabbitMq:User' 'bandup' --project $bandupProject
    dotnet user-secrets set 'RabbitMq:Password' $bandupRabbitPassword --project $bandupProject
}
```

The API also needs a signing key. Generate it once for your local environment; replacing it
invalidates existing access JWTs:

```powershell
$bandupKeyBytes = New-Object byte[] 32
$bandupRng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
try {
    $bandupRng.GetBytes($bandupKeyBytes)
    dotnet user-secrets set 'Auth:SigningKey' ([Convert]::ToBase64String($bandupKeyBytes)) --project src/BandUp.Api
}
finally {
    $bandupRng.Dispose()
}
dotnet user-secrets set 'Captcha:Provider' 'Fake' --project src/BandUp.Api
dotnet user-secrets set 'Auth:RequireSecureCookies' 'false' --project src/BandUp.Api
dotnet user-secrets set 'Swagger:Enabled' 'true' --project src/BandUp.Api
```

The Worker does not need the signing key or CAPTCHA settings. The fake CAPTCHA provider
accepts exactly `fake-captcha-token`. It allows Swagger-only testing without frontend keys
or a challenge widget. Real Turnstile testing needs `Captcha:Provider=Turnstile`, the real
secret, and fresh challenge tokens generated by a client integration; Swagger has no widget.

The API now also requires an independent recovery-code protection key at startup. Keep your
existing key if already configured; otherwise generate it once with the commands below.
Do not reuse `Auth:SigningKey`. Rotating this key invalidates outstanding reset codes and
changes recovery quota identities. The Worker does not need this key.

```powershell
$bandupRecoveryKeyBytes = New-Object byte[] 32
$bandupRecoveryRng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
try {
    $bandupRecoveryRng.GetBytes($bandupRecoveryKeyBytes)
    dotnet user-secrets set 'PasswordReset:CodeProtectionKey' ([Convert]::ToBase64String($bandupRecoveryKeyBytes)) --project src/BandUp.Api
}
finally {
    $bandupRecoveryRng.Dispose()
}
dotnet user-secrets set 'PasswordReset:RateLimitProvider' 'Redis' --project src/BandUp.Api
```

## 3. Migrate and start the API

```powershell
dotnet run --project src/BandUp.Api --launch-profile http -- --migrate
dotnet run --project src/BandUp.Api --launch-profile http -- --urls http://localhost:18080
```

The second command overrides the launch profile's default port 8080. Port 18080 is an example,
not a guaranteed free port. For Windows socket error 10013, inspect both excluded ranges and
choose an available port:

```powershell
netsh interface ipv4 show excludedportrange protocol=tcp
netsh interface ipv6 show excludedportrange protocol=tcp
```

Keep using the same API host and scheme during a test. Cookies are scoped by host/path, not
by port. Open `/ready` on the selected origin, then `/swagger`:

- `http://localhost:18080/ready` should return `200` with no pending migrations.
- `http://localhost:18080/swagger` opens the API's own Swagger UI.

Local HTTP works because `Auth:RequireSecureCookies=false`. The production policy uses HTTPS
and secure cookies. `HttpOnly` prevents JavaScript from reading tokens; the browser still
stores and sends the cookies. Same-origin Swagger needs no manual JWT entry.

## 4. Exercise the auth flow in Swagger

Clear stale `bu_at` and `bu_rt` cookies for this host before a fresh walkthrough, especially
after changing the signing key. In Development, Swagger automatically adds the required
`X-Requested-With: bandup` header to same-origin JSON API mutations. The server's CSRF guard
remains enabled.

Register a unique email with `POST /api/auth/register`:

```json
{
  "email": "local-tester@example.com",
  "password": "ExamplePass123!",
  "displayName": "Local Tester",
  "captchaToken": "fake-captcha-token"
}
```

Registration returns `201` and creates the signup credit account. It does not sign in.
Call `POST /api/auth/login`:

```json
{
  "email": "local-tester@example.com",
  "password": "ExamplePass123!",
  "captchaToken": "fake-captcha-token"
}
```

Login returns `200` and sets the cookies. Then follow this sequence:

| Call | Request body | Expected result |
|---|---|---|
| `GET /api/auth/me` | None | `200` with the profile and current credit balance |
| `POST /api/auth/refresh` | `{}` | Empty `200`; both cookies are replaced |
| `GET /api/auth/me` | None | `200` using the renewed cookies |
| `POST /api/auth/logout` | `{}` | Empty `204`; both cookies are deleted |
| `GET /api/auth/me` | None | `401 UNAUTHORIZED` |
| `POST /api/auth/refresh` | `{}` | `401 INVALID_REFRESH_TOKEN` because the refresh cookie is missing |

Run these sequentially. Strict reuse detection intentionally rejects parallel refreshes and
revokes the user's remaining refresh sessions. If the access token expires before logout,
complete a refresh first, then logout using the updated browser cookies.

The login response currently has a placeholder credit balance; `/me` is the source of the
actual balance. See [implementation status](implementation-status.md) for deferred issues.

## 5. Use another HTTP client

Send both `Content-Type: application/json` and `X-Requested-With: bandup` on state-changing
requests carrying either session cookie. Refresh and logout require `{}` as their JSON body.
Tokens come from cookies, never body fields, query parameters or bearer headers.

For PowerShell, use a web session so it retains replacement/deletion cookies:

```powershell
$bandupApi = 'http://localhost:18080'
$bandupHeaders = @{ 'X-Requested-With' = 'bandup' }
$bandupLogin = @{
    email = 'local-tester@example.com'
    password = 'ExamplePass123!'
    captchaToken = 'fake-captcha-token'
} | ConvertTo-Json
Invoke-WebRequest "$bandupApi/api/auth/login" -Method Post -ContentType 'application/json' -Headers $bandupHeaders -Body $bandupLogin -SessionVariable bandupSession
Invoke-WebRequest "$bandupApi/api/auth/me" -WebSession $bandupSession
Invoke-WebRequest "$bandupApi/api/auth/refresh" -Method Post -ContentType 'application/json' -Headers $bandupHeaders -Body '{}' -WebSession $bandupSession
Invoke-WebRequest "$bandupApi/api/auth/logout" -Method Post -ContentType 'application/json' -Headers $bandupHeaders -Body '{}' -WebSession $bandupSession
```

For browser integration and concurrency rules, see [the client contract](auth-client-contract.md).
For automated acceptance coverage, see [the acceptance matrix](auth-session-acceptance.md).

## 6. Test forgotten-password recovery with a local inbox

No email-provider account, payment, SMTP credentials or frontend is required for this local
flow. Mailpit captures messages on your computer; it does not send to a real mailbox. Use
any valid test address registered through the API. Start the optional recovery profile:

```powershell
docker compose --env-file infra/env/dev.env -f infra/docker/docker-compose.dev.yml --profile recovery up -d --wait
dotnet user-secrets set 'Email:Provider' 'Mailpit' --project src/BandUp.Api
dotnet user-secrets set 'Email:MailpitBaseUrl' 'http://localhost:8025/' --project src/BandUp.Api
dotnet user-secrets set 'Email:FromEmail' 'no-reply@bandup.local' --project src/BandUp.Api
dotnet user-secrets set 'Email:FromName' 'BandUp local' --project src/BandUp.Api
```

Open `http://localhost:8025/` and confirm the inbox is available, then restart the API with
the command in section 3. If 8025 is unavailable, set `MAILPIT_HTTP_PORT` in the ignored
`dev.env` and use that same port in `Email:MailpitBaseUrl`. Only the HTTP inbox/send API is
published, bound to loopback; no SMTP port is needed. Mailpit data is disposable: recreating
its container removes the captured messages. No reset code is exposed by an API debug route.

`Email:Provider=InMemory` remains the safe offline default, but that inbox is accessible only
through DI/tests. Select Mailpit for a human-readable inbox. Keep `PasswordReset:RateLimitProvider=Redis`
for the normal local stack; `InMemory` quotas are process-local and reset on restart.

In Swagger, request a code with `POST /api/auth/forgot-password`:

```json
{
  "email": "local-tester@example.com"
}
```

The response is `202` with the same generic message for eligible, unknown, inactive and
email-suppressed accounts. Read the six-digit code from Mailpit, then call
`POST /api/auth/reset-password`:

```json
{
  "email": "local-tester@example.com",
  "code": "012345",
  "newPassword": "ChangedPass456!"
}
```

Replace `012345` with the actual code. Keep it a JSON string to preserve leading zeroes.
No CAPTCHA or existing login is required for either recovery endpoint. With session cookies
present, the existing JSON/custom-header CSRF requirements still apply; Development Swagger
adds `X-Requested-With: bandup` for these requests too.

| Check | Expected result |
|---|---|
| Correct unused code within 10 minutes | Empty `204`; both current browser session cookies are deleted |
| `GET /api/auth/me` immediately afterward | `401`; reset does not sign in automatically |
| Login with the old password | `401 INVALID_CREDENTIALS` |
| Login with the new password | `200`; normal session cookies are issued |
| Reuse the successful code, or submit a wrong/expired/exhausted code | Generic `422 INVALID_PASSWORD_RESET_CODE`; cookies are preserved |
| Five incorrect guesses for one code | The fifth exhausts it; a subsequent correct code is rejected |
| Immediate resend within 60 seconds | Same `202`; no replacement email, existing code stays valid |
| Permitted resend after cooldown and within quotas | Same `202`; a new message replaces the previous challenge |
| Malformed email/code/password | `400 VALIDATION_ERROR` |
| Client-IP-wide quota exhausted | `429 PASSWORD_RESET_RATE_LIMITED` |

A successful reset revokes the account's stored refresh tokens and queues a second Mailpit
message confirming the password change. Copied access JWTs on other devices retain their
normal expiry (default 15 minutes plus up to 30 seconds of validation skew). Passwords are
10–128 characters with a letter and digit; whitespace in passwords is not trimmed.

Email delivery is asynchronous and best-effort. A `202` is an acknowledgement, not proof of
delivery. If Mailpit is unavailable, the committed request still gets the same response;
restore the inbox and request another code after the cooldown. Starting Mailpit later does
not replay failed deliveries. For real delivery through Resend, continue with section 7.

## 7. Use Resend and a real inbox in Swagger

Run the PowerShell commands below from the repository root. Keep your existing database,
Redis, RabbitMQ, `Auth:SigningKey` and `PasswordReset:CodeProtectionKey` secrets. Do not clear
the stores or regenerate working keys. If setting up from scratch, finish sections 1–3 first.
The API's outbound connection to Resend uses HTTPS even when Swagger runs on local HTTP.
The frontend, standalone Worker and Mailpit are not needed for this flow.

### Choose the sender and recipient

- For a first test without a verified domain, use `onboarding@resend.dev` as the sender.
  The recipient must be the email address associated with your Resend account. Register
  that same real address in BandUp; a Mailpit test account at `example.com` will not work.
- To send recovery codes to other users, add and verify a domain you control in Resend and
  choose a sender on that exact verified domain, for example `no-reply@your-domain.com`.
  Domain verification requires the DNS records supplied by Resend. A personal Gmail address
  is not a substitute for a verified sending domain.
- Create/use a Resend key with sending permission for the selected sender/domain. This
  application only sends email; it does not need permissions to administer your account.

These restrictions come from [Resend's test-domain documentation](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain).
See also [API key management](https://resend.com/docs/dashboard/api-keys/introduction) and
[the email submission API](https://resend.com/docs/api-reference/emails/send-email).

### Set API user secrets

Enter the actual key at the hidden prompt; it is not written into this script or the repo:

```powershell
$bandupResendKey = Read-Host 'Resend API key' -AsSecureString
try {
    dotnet user-secrets set 'Email:ResendApiKey' ([System.Net.NetworkCredential]::new('', $bandupResendKey).Password) --project src/BandUp.Api
}
finally {
    $bandupResendKey.Dispose()
    Remove-Variable bandupResendKey
}
dotnet user-secrets set 'Email:Provider' 'Resend' --project src/BandUp.Api
dotnet user-secrets set 'Email:FromEmail' 'onboarding@resend.dev' --project src/BandUp.Api
dotnet user-secrets set 'Email:FromName' 'BandUp' --project src/BandUp.Api
dotnet user-secrets set 'PasswordReset:RateLimitProvider' 'Redis' --project src/BandUp.Api
dotnet user-secrets set 'Captcha:Provider' 'Fake' --project src/BandUp.Api
dotnet user-secrets set 'Auth:RequireSecureCookies' 'false' --project src/BandUp.Api
dotnet user-secrets set 'Swagger:Enabled' 'true' --project src/BandUp.Api
```

For a verified domain, replace the `Email:FromEmail` value with your real sender instead.
`Email:ResendApiKey` authenticates email submission; `PasswordReset:CodeProtectionKey`
protects stored OTPs; `Auth:SigningKey` signs access JWTs. Keep these three keys independent.
Never put the Resend key in Swagger, frontend code, request JSON or `dev.env`. The Worker
does not need these new email secrets. Restart the API after changing settings.

Startup checks the selected provider, key format, sender and timeout settings. It cannot
verify that the key is active or the domain is verified; Resend checks those when sending.

### Start and test

```powershell
docker info
docker compose --env-file infra/env/dev.env -f infra/docker/docker-compose.dev.yml up -d --wait
dotnet run --project src/BandUp.Api --launch-profile http -- --migrate
dotnet run --project src/BandUp.Api --launch-profile http -- --urls http://localhost:18080
```

Open `http://localhost:18080/ready`, then `http://localhost:18080/swagger`. Keep one host and
scheme throughout the walkthrough. Development Swagger supplies the CSRF header for JSON
mutations; the browser manages the HttpOnly cookies. No bearer token entry is required.

In all JSON below, replace `your-account-email@example.com` with your actual receiving email.
For the test sender this must be your Resend account email.

1. Register through `POST /api/auth/register` (skip registration if that user already exists):

   ```json
   {
     "email": "your-account-email@example.com",
     "password": "ExamplePass123!",
     "displayName": "Recovery Tester",
     "captchaToken": "fake-captcha-token"
   }
   ```

   Expect `201`. Existing email returns `409`; continue with that existing account. This
   flow requires an active account. Registration itself does not send a recovery email.

2. Call `POST /api/auth/login` using the same email, its current password and
   `captchaToken: "fake-captcha-token"`. Expect `200`, then `GET /api/auth/me` returns `200`.
   This login is optional for recovery; it makes cookie clearing observable.

3. Call `POST /api/auth/forgot-password`:

   ```json
   { "email": "your-account-email@example.com" }
   ```

   Expect generic `202`. Wait for the email in your real inbox (also check spam). The code
   is generated and protected by BandUp; Resend only transports the email. The raw code is
   never returned by Swagger/API or persisted in the database.

4. Copy the actual six-digit code into `POST /api/auth/reset-password`:

   ```json
   {
     "email": "your-account-email@example.com",
     "code": "012345",
     "newPassword": "ChangedPass456!"
   }
   ```

   Replace `012345` with the received code, keeping it a string. Submit before its ten-minute
   expiry. The code and new password are checked in this one endpoint; there is no separate
   code-verification endpoint. Expect empty `204`, cookie deletion, and a second email
   confirming the password change. The new password is never sent to Resend.

5. `GET /api/auth/me` now returns `401`. Login with the old password returns
   `401 INVALID_CREDENTIALS`; login with `ChangedPass456!` returns `200`. `GET /me`, refresh
   with `{}`, and logout with `{}` then work normally as described in section 4.

6. Reusing the successful code returns `422 INVALID_PASSWORD_RESET_CODE`. A wrong, expired,
   consumed or exhausted code uses that same response. Five incorrect guesses exhaust a
   challenge. Request another code through `forgot-password` after the 60-second cooldown,
   subject to quotas; an admitted replacement invalidates the previous code.

### If the email does not arrive

`202` acknowledges the request; it is not proof of delivery. Delivery runs after commit in
the API's background worker. A failed send does not undo the saved challenge or reveal the
recipient/account state through the HTTP response. There is no automatic retry or durable
outbox; a process restart can lose pending messages. Request a fresh code after cooldown
once the cause is fixed. Provider acceptance also does not guarantee inbox placement.

| Symptom | Check |
|---|---|
| API fails on `Email:ResendApiKey` | Set a `re_...` key in the API user-secret store and restart |
| API fails on sender configuration | Set `Email:FromEmail`; the `.local` Mailpit sender cannot be used with Resend |
| No message appears in Resend | Check the selected provider, active BandUp account, cooldown/quotas and sanitized API delivery warnings |
| Resend reports `401` | The key may be invalid, deleted or inactive |
| Resend reports `403` | Check domain verification, sender/domain permission and the test sender's account-email-only restriction |
| Resend reports `429` | Check provider rate limits/quota as well as BandUp's separate recovery quotas |
| Resend accepts the email but the inbox is empty | Check the recipient, spam folder, delivery/bounce status and sender DNS |
| Swagger returns `400` with existing cookies | Use same-origin Development Swagger or send `X-Requested-With: bandup` and JSON |
| Swagger returns `422` during reset | Use the latest code, exact email and a code that is unused, unexpired and not exhausted |

The API logs sanitized failure types; inspect your Resend dashboard for provider details.
No code/key/provider response body is printed in API logs. Resend's
[error reference](https://resend.com/docs/api-reference/errors) explains provider statuses.

To return to local Mailpit, keep the key stored and change the selected provider/sender:

```powershell
dotnet user-secrets set 'Email:Provider' 'Mailpit' --project src/BandUp.Api
dotnet user-secrets set 'Email:FromEmail' 'no-reply@bandup.local' --project src/BandUp.Api
```

Start the `recovery` profile from section 6 and restart the API. Selecting `InMemory` instead
also works offline, but its inbox is accessible only through DI/tests. Automated Resend
tests use a fake HTTP transport and test credentials; they never send real emails.
